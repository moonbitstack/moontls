The guide·install · connect · record · key · resume · datagram

Everything, in the order you need it

Ten sections, each one running: the second depends on the first and nothing before is repeated. The blocks that compute — a record, the key schedule, an alert, a suite's registry name — are compiled by this repository's build, with the output printed beside them; the ones that are a loop around somebody else's socket are sketches of that loop.

03 00 00 011 · Install

Add the module and import the package that does the work. Nothing else is needed at run time: no C library, no provider module, no environment variable.

moon add moonbitstack/moontls@0.9.16

The library has no I/O of its own, so a program that only computes — a key schedule, a record, an alert — needs nothing else. A program that talks to a network brings its own socket, and that is the next section.

01 00 00 002 · The client loop

A connection is three calls, repeated until the handshake opens. The client speaks first, so it has bytes to send before any arrive; after that it alternates: what the socket gave, then what the connection wants to send.

let config = @tls.Client::new(@roots.mozilla(), alpn=["h2", "http/1.1"])
let conn = @tls.Conn::client(config, "example.com", rand~, now~)
socket.write(conn.take())                     // the ClientHello
while !conn.is_connected() {
  conn.receive(socket.read()[:])
  socket.write(conn.take())
}

rand is a function of one argument that returns that many random octets; now is the wall clock in seconds, which is the clock a certificate is judged against. Both are parameters because a protocol state machine with no entropy and no clock of its own can be replayed by a test.

The loop is not a formality: one receive may be half a record, and one take may be a whole flight. Feed it the octets as they arrive and write out whatever it hands back; it will not ask twice.

02 00 00 003 · The other end

A server is the same type with the other first step. It is constructed with the chain — leaf first — and the key that matches the leaf, and it refuses at construction if the two do not belong together, which is one handshake's worth of debugging saved.

let chain = @x509.pems(cert_pem)                              // leaf first
let config = @tls.Server::new(chain, @x509.PrivateKey::pem(key_pem), alpn=["h2"])
let server = @tls.Conn::server(config, rand~)

The two ends fit together without a socket, which is how the tests in this repository run a handshake: make one of each, and pass take to receive in both directions until neither has anything left to say. A test that does that reaches the same states a network does, and fails the same way.

17 03 03 00 164 · What was agreed

Once the handshake is open the connection answers what a caller has to branch on: the version, the suite, the group, the ALPN protocol, the server's name, and the peer's chain.

conn.version()          // Some(Tls13)
conn.suite()            // Some(ChaCha20Poly1305) on a 1.3 connection
conn.suite12()          // Some(...) on a 1.2 one, None on 1.3
conn.alpn()             // Some("h2") when both ends named it
conn.server_name()      // Some("example.com"), as the client asked
conn.peer()             // the chain, leaf first; empty when resumed

A resumed handshake is authenticated by its ticket, so peer() is empty on both ends unless a client certificate was asked for again. That is what is_resumed() is for.

17 03 03 00 135 · The layer under it

The record layer can be used on its own, which is what a test does when it wants to know that a key, a nonce and a content type come out as the octets a specification prints. One secret, one suite, one record.

test {
  let suite = @record.Aes128Gcm
  let secret = @base16.decode("ab4fc9e2370723165814c074381ab62cbb2c32fd421b15db6910f5df5b1756a3")
  let writer = @record.Cipher::new(secret[:], suite~)
  let record = writer.seal(@record.Handshake, b"hello"[:])
  assert_eq(@base16.encode(record[:]), "1703030016ea041db0127f9d1812962e71632919c00bfbe245872d")
  // The same secret on the other side opens it: the content type moved inside, and came back.
  let reader = @record.Cipher::new(secret[:], suite~)
  let (kind, content) = reader.open(record[:])
  assert_eq(kind, @record.Handshake)
  assert_eq(content, b"hello")
}

The key schedule is a ladder of calls, each taking the secret above it and saying what it is for. A digest is a parameter all the way down, because RFC 8446 writes the ladder over the hash the suite names.

test {
  let early = @keys.early()                       // no PSK: the zero secret
  let shared = b"\x8b\xd4\x05\x4f\xb5\x5b\x9d\x63\xfd\xfb\xac\xf9\xf0\x4b\x9f\x0d\x35\xe6\xd6\x3f\x53\x75\x63\xef\xd4\x62\x72\x90\x0f\x89\x49\x2d"
  let handshake = @keys.handshake(early[:], shared[:])   // salted by the key exchange
  let transcript = @keys.Transcript::new()
  transcript.add(b"\x01\x00\x00\x00"[:])              // a ClientHello, for the shape of it
  let secret = @keys.client_handshake(handshake[:], transcript.hash()[:])
  assert_eq(
    @base16.encode(secret[:]),
    "ab4fc9e2370723165814c074381ab62cbb2c32fd421b15db6910f5df5b1756a3",
  )
}

A failure is an alert, not an exception with a message. @alert.Alert carries the level and the kind, and kind is the number the wire uses, so a caller can map it to whatever its own transport reports.

test {
  let alert = @alert.fatal(@alert.BadRecordMac)
  assert_eq(@alert.encode(alert), b"\x02\x14")
  assert_eq(@alert.BadRecordMac.name(), "bad_record_mac")
}

14 03 03 00 016 · The older version

TLS 1.2 is on by default beside 1.3, and its suites are a table, one row per suite: the exchange, the certificate type, the protection, the hash. A caller that wants only some of them names them; @tls.suites12 is the six with ECDHE and an AEAD, and @record.all12 is the whole table.

test {
  let suite = @record.Suite12::of(0xc02b).unwrap()
  assert_eq(suite.name(), "TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256")
  assert_eq(suite.exchange, @record.Ecdhe)
  assert_eq(@record.all12.length(), 39)
}

The old suites keep their countermeasures. A CBC record does the same work whatever is wrong with it, and a wrapped premaster secret that fails to unwrap becomes a random one that fails at Finished: Lucky Thirteen and Bleichenbacher, in the code rather than in a paragraph.

TLS 1.1 and 1.0 are implemented and left out of the preset, as RFC 8996 asks. Naming them in versions is the whole of the consent, and with it come MD5-and-SHA-1's PRF, the implicit CBC IV, and the signature that has no scheme on the wire.

let config = @tls.Client::new(roots, versions=[Tls13, Tls12, Tls11, Tls10])

17 03 03 00 337 · Coming back

A session can be resumed instead of authenticated again. In TLS 1.3 the server hands out tickets sealed under its own keys — the ticket carries the state, so the server keeps nothing — and a client offers one back as a pre-shared key with a binder over the truncated hello. Hand the same Sessions store to every connection and the second one finds what the first left.

let store = @tls.Sessions::new()
let config = @tls.Client::new(@roots.mozilla(), sessions=store)
// The first connection collects tickets; the second offers one, and resumes.

0-RTT is the same ticket, used earlier. A client that asks writes before the server has answered, and the server decides: accepted, the data is read under the early key; declined, the client sends it again as ordinary data, so a caller sees its bytes arrive once, in order, either way. early_accepted() says which.

let conn = @tls.Conn::client(config, host, rand~, now~, early=true)
conn.write_early(b"GET / HTTP/1.1\r\n\r\n"[:])
// ... hand the octets over ...
conn.early_accepted()    // true when the server took it

0-RTT is off until a server says otherwise with Tickets::new(keys, early=n). The data can be replayed by whoever recorded it; that is RFC 8446 §8, and a default of zero is the only honest one.

16 fe fd 00 008 · Datagrams

DTLS is the same handshake over a transport that loses, reorders and duplicates. The connection takes a clock, because what a datagram costs is time: deadline() says when the next tick() is due, and tick() retransmits what is overdue.

let conn = @dtls.Conn13::client(config, "example.com", rand~, now~, wall~)
socket.send(conn.take())
while !conn.is_connected() {
  conn.receive(socket.recv()[:], now~=monotonic_ms())
  socket.send(conn.take())
  if conn.deadline() is Some(due) && monotonic_ms() >= due {
    conn.tick(now~=monotonic_ms())
  }
}

A record that does not deprotect — a duplicate caught by the replay window, a forgery — is dropped and the association goes on, which is the difference between a datagram and a stream. DTLS 1.3 acknowledges records and resends the fragments no ACK named; DTLS 1.2 has no ACK, and its answer is what acknowledges a flight.

A server can refuse to keep state until the address has proved it can receive. Pass cookie=@dtls.Cookie::Key(key) and the first hello is answered with a retry carrying a cookie; the cookie holds the hash of that hello, so an instance that kept nothing can finish the handshake the next one began.

1c 00 00 009 · QUIC, and any other transport

QUIC needs the TLS 1.3 handshake and none of TLS's record layer. quic_client and quic_server are that handshake with the records taken out: crypto takes the bytes from a CRYPTO frame, and steps hands back what to send, at which level, and when each level has keys. No records, no change_cipher_spec, no alerts on the wire.

for step in conn.steps() {
  match step {
    Send(level, bytes) => transport.crypto(level, bytes)
    Keys(level, ..) => transport.level_ready(level)
    Early(..) => ()
  }
}

A third transport is the same seam: tls.Layer is what a record layer implements, and tls.Handshake is the handshake bound to one. Nothing in the library knows which of the three it is running over.

02 00 00 2810 · Judging it

The repository keeps both of its judges in reach: scripts/tls_interop.sh drives this library against OpenSSL, BoringSSL, Go's crypto/tls, Python's ssl and pion/dtls, in both directions, and scripts/tls_fuzz.sh runs tlsfuzzer's TLS 1.3 conversations against the server. The peer program they drive is a separate module under integration/, so the library's own dependencies stay what the library needs.

What those runs found, and what is still open, is in the README's conformance section, one line per case rather than a percentage.
