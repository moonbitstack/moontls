17 03 03 00 2aWhat it is

ciphertext in, events out

Every call takes the octets a socket gave you and returns the octets to send. Buffers, flights and retransmissions are yours to drive; nothing here knows what a file descriptor is.

no cryptography of its own

The AEADs, hashes, key exchanges and signatures are another module's. Certificate chains are judged by another module's. This one is the protocol: the record layer, the key schedule, the state machine.

one type, both ends

A client and a server are the same Conn with a different first step, so a test can hold both ends and hand the bytes across without a network in between.

14 03 03 00 01The shape of a connection

Three calls: hand over what arrived, take what should go out, read what came out in the clear. A client speaks first, so it has a hello to send before anything arrives.

a client

let config = @tls.Client::new(@roots.mozilla(), alpn=["h2", "http/1.1"])
let conn = @tls.Conn::client(config, "example.com", rand~, now~)
socket.write(conn.take())                     // the ClientHello
while !conn.is_connected() {
  conn.receive(socket.read()[:])
  socket.write(conn.take())
}
conn.alpn()                                   // Some("h2")
conn.write(request[:])

a server, with the same three calls

let chain = @x509.pems(cert_pem)                              // leaf first
let config = @tls.Server::new(chain, @x509.PrivateKey::pem(key_pem), alpn=["h2"])
let server = @tls.Conn::server(config, rand~)

These are the blocks the README shows, and the build compiles them on every commit.

16 03 03 00 04What it speaks

SurfaceDetail
TLS 1.3RFC 8446 — HelloRetryRequest, middlebox compatibility mode, KeyUpdate, close_notify, declined 0-RTT read past
TLS 1.2RFC 5246 — every suite in its table: RSA, DHE and ECDHE exchange, AES-GCM, CCM, ChaCha20-Poly1305, CBC with Lucky Thirteen's fix, encrypt-then-MAC
TLS 1.1 · 1.0RFC 4346, RFC 2246 — off unless a caller names them, as RFC 8996 asks
DTLS 1.3 · 1.2RFC 9147, RFC 6347 — replay window, ACKs, fragmentation, the stateless cookie
Key exchangeX25519MLKEM768 first, then X25519, P-256, P-384, P-521, X448; SecP256r1MLKEM768, SecP384r1MLKEM1024 and ML-KEM alone on request; the RFC 7919 groups, and brainpool's
CertificatesECDSA, RSA-PSS, Ed25519 and ML-DSA; client certificates in both versions, including the post-handshake request; OCSP stapling; RFC 8879 compression
ResumptionTickets and 0-RTT in 1.3, session ids and RFC 5077 tickets in 1.2; a ticket's age across two clocks
Beside themALPN, SNI, secure renegotiation, record_size_limit, DTLS-SRTP keying material, and the QUIC handshake seam

17 03 03 00 13Packages

PackageWhat lives there
wireinteger widths, the frozen legacy_version, and the cursor every decoder reads through
alertthe alert protocol, with no dependencies of its own
keysthe key schedule, the transcript, and the two label prefixes TLS and DTLS use
recordthe record layer and TLS 1.2's suite table
extwhat the extensions are on the wire, and nothing about what to pick from them
msgthe handshake messages, as formats only
hsnegotiation, HelloRetryRequest, and which message may arrive next
dtlswhat datagrams change, and the two connections over them
srtpthe SRTP profiles a DTLS handshake negotiates, and the keys exported for them
tlsthe connection itself: client and server, 1.0 to 1.3, and the QUIC seam

The split is deliberate: a tool that has to read a ClientHello — a router, a fingerprinter — can do it without linking a handshake or a record layer.
